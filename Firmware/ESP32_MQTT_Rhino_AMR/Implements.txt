     |           |

2) REEMAN RHINO — HTTP WEB API (SLAM WEB API 3.0)
--------------------------------------------------------------------------------
Source docs:
  - REEMAN SLAM WEB API 3.0-2024-06-03.pdf

  - REEMAN FORKLIFT CALLING API.pdf

Replace (host) with robot navigation IP, e.g. 192.168.1.50
Client must be on the same LAN as the navigation system.

Content-Type for bodies: application/json  (unless noted)

--- STATUS / SENSOR (mostly GET) ---

GET  http://(host)/reeman/current_version
     → {"version":"v1.1.0"}

GET  http://(host)/reeman/pose
     → {"x":2.97,"y":2.51,"theta":0.97}

GET  http://(host)/reeman/get_mode
     → {"mode":2}   // 1=mapping, 2=navigation

GET  http://(host)/reeman/hostname
     → {"hostname":"reeman-robot"}

GET  http://(host)/reeman/imu
     → {"a":0.0,"g":0.0}   // exception = fault

GET  http://(host)/reeman/laser
     → {"coordinates":[[364,166],...]}

GET  http://(host)/reeman/base_encode
     → {"battery":100,"chargeFlag":1,"emergencyButton":0}
       chargeFlag: 2=dock charging, 3=adapter, 8=docking, other=not charging
       emergencyButton: 0=pressed, 1=released

GET  http://(host)/reeman/speed
     → {"vx":0.3,"vth":0.5}   // vx m/s, vth deg/s (doc wording)

GET  http://(host)/reeman/nav_status
     → {"res":3,"reason":0,"goal":"A","dist":1.8,"mileage":2.3}
       res=1 start, res=3 done (reason 0 success / 1 fail),
       res=4 cancelled, res=6 special reasons (e-stop, charge, no goal, etc.)

GET  http://(host)/reeman/global_plan
     → {"coordinates":[[0.826,-0.35],...]}

3) REEMAN FORKLIFT CALLING — MQTT API
--------------------------------------------------------------------------------
Source: REEMAN+FORKLIFT+CALLING+API.pdf

Broker:  mqtt.rmbot.cn
Port:    1883

Pairing (UDP multicast before MQTT):
  Multicast IP:   239.0.0.1
  Multicast port: 7979
  Robot broadcasts when in pairing mode:
    {"hostname":"...","alias":"...","key":"...","token":"...","robotType":9}
  robotType 9 = forklift (Rhino family)

IMPORTANT:
  - Task payloads use AES encryption with pairing key
  - Heartbeat from phone must arrive within 10 s or robot ignores commands
  - Robot heartbeat after wake: every 5 s
  - This cloud calling MQTT is for mapped tasks, NOT simple joystick move
  - For local floor collision avoidance, prefer LOCAL broker + HTTP /cmd/*

Phone → Robot topics (publish):
  reeman/calling/phone/{hostname}/forklift/heartbeat
      {"token":"..."}

  reeman/calling/phone/{hostname}/forklift/points/request/calling_model
  reeman/calling/phone/{hostname}/forklift/points/request/auto_model
  reeman/calling/phone/{hostname}/forklift/points/request/manual_model
  reeman/calling/phone/{hostname}/forklift/points/request/task_model
      {"token":"..."}

  reeman/calling/phone/{hostname}/forklift/task/calling_model
  reeman/calling/phone/{hostname}/forklift/task/auto_model
  reeman/calling/phone/{hostname}/forklift/task/manual_model
  reeman/calling/phone/{hostname}/forklift/task/task_model
      {"token":"...","body":"<AES encrypted>"}

  Calling body (before AES): {"map":"map1","point":"point1"}
  Auto body: list of {first:{map,point}, second:{map,point}} pairs
  Manual body: {first:null, second:"point"}
  Task body: "routeName" string

Robot → Phone topics (subscribe):
  reeman/calling/robot/{hostname}/forklift/heartbeat
      status: battery, e-stop, navigating, currentTask, taskList, ...

  reeman/calling/robot/{hostname}/forklift/points/response/calling_model
  reeman/calling/robot/{hostname}/forklift/points/response/auto_model
  reeman/calling/robot/{hostname}/forklift/points/response/manual_model
  reeman/calling/robot/{hostname}/forklift/points/response/task_model
      {"token":"...","code":0,"body":"<AES>"}  // code 0=ok decrypt, 1=error plaintext

  reeman/calling/robot/{hostname}/forklift/task/response
      code 0=task started, 2=cannot start

HTTP vs MQTT on Rhino (remember this):
  HTTP /cmd/move, /cmd/speed, /cmd/nav_name  →  local Wi-Fi direct control
  MQTT mqtt.rmbot.cn calling topics          →  paired task/point calling
  Your factory floor MQTT (Mosquitto)        →  multi-AMR traffic + sensors

4) LOCAL FLOOR MQTT TOPIC MAP (your system — design now)
--------------------------------------------------------------------------------
Use a LOCAL broker (Mosquitto on PC or industrial PC). Do NOT rely on
broker.emqx.io for production floor control.

Suggested topics:

  floor/{site}/amr/{amr_id}/pose          // publish: x,y,theta,ts
  floor/{site}/amr/{amr_id}/status        // battery, e-stop, mode, goal
  floor/{site}/amr/{amr_id}/cmd           // go_point / stop / cancel
  floor/{site}/zone/{zone_id}/lock        // "free" | "held_by:AMR1"
  floor/{site}/point/{point_id}/reservation
  floor/{site}/traffic/event              // conflict, yield, clear
  floor/{site}/conveyor/{line_id}/vision  // product OK / jam / missing
  floor/{site}/rfid/{reader_id}/tag       // tag UID + timestamp
  floor/{site}/camera/{cam_id}/event      // detect events (not raw video)
  floor/{site}/estop                      // global soft stop flag

Collision rule (simple v1):
  Before AMR goes to Point A:
    1) Publish reservation request for point A
    2) Floor manager grants lock only if free
    3) Winner navigates via HTTP POST /cmd/nav_name {"point":"A"}
    4) On arrival / cancel, release lock
    5) Loser waits or takes alternate point/path

ESP32 role later:
  MQTT subscribe cmd → translate → HTTP POST to Rhino IP
  OR publish Rhino status polled via HTTP GET onto MQTT

--------------------------------------------------------------------------------
6) LEARNING TRACK (API + NETWORKING + MQTT)
--------------------------------------------------------------------------------
Networking:
  - IP = address on LAN; MAC = hardware NIC id
  - Same subnet needed for HTTP to ROBOT_IP
  - Ports: 80 (HTTP API), 1883 (MQTT), 7979 (UDP pairing multicast)
  - Gateway / DHCP / static IP for robots

HTTP methods (Postman):
  GET    = read status (pose, battery, mode)
  POST   = send command (move, nav, charge, map ops)
  DELETE = remove resource (waypoint delete)
  PUT    = replace resource (not heavily used in this Reeman doc set)

MQTT vs HTTP:
  HTTP  = request/response to ONE robot IP (best for motion commands)
  MQTT  = many devices share topics (best for fleet traffic + sensors)
  Combine both: MQTT for coordination, HTTP for actual Rhino motion

Think of it like a walkie-talkie call box for a robot forklift.

The big idea
Your ESP32 is a small remote.

It turns on
It finds the Wi‑Fi
It joins the laptop’s chat room (Mosquitto)
It listens for the robot saying “I’m OK”
When you press A or S, it tells the robot where to go
No Python dashboard — the ESP32 talks to the robot itself.

Like a story
When you plug in power or press RESET:

Blue light — “I’m waking up and looking for Wi‑Fi.”
It joins Wi‑Fi, gets an IP address.
Still blue — “I’m calling the chat room on the laptop.”
If Mosquitto is running → MQTT ok.
Purple light — “Waiting for the robot to say hello.”
When the robot sends STATUS (battery=...) → green (ready).
Screen says: press A for home, S for p1.
When you press A:

ESP32 writes a secret note (AES encryption) that says “go to home”
Sends it on the chat room
Bright green — “I sent it / robot may be moving”
When you press S:

Same, but “go to p1”
Who talks to whom
You → ESP32 → Laptop chat room (Mosquitto) → Robot
Robot → chat room → ESP32 (battery / moving / stop)
Safety checks (why it sometimes says “not healthy”)
Before sending a move, it asks:

Did I hear the robot recently?
Is the emergency stop released?
Is the robot not already busy?
Is the battery high enough?
